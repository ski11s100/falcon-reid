# Проектное решение «ФАЛЬКОН»

## 1. Гипотеза

Одного номера недостаточно для межкамерного поиска автомобиля. Устойчивый идентификатор должен объединять независимые сигналы: нейросетевой визуальный эмбеддинг, геометрию кузова, цвет, марку/модель, локальные особенности и, когда доступно, распознанный номер.

Итоговый балл в промышленной версии:

`score = 0.65 × ReID + 0.12 × цвет + 0.10 × тип/модель + 0.08 × локальные детали + 0.05 × номер`

Веса должны калиброваться на проверочной части конкурсного датасета. Номер не должен блокировать совпадение при низкой уверенности OCR.

## 2. Конвейер

1. Получить кадр и проверить его качество.
2. Найти автомобиль детектором и вырезать область кузова.
3. Нормализовать размер и яркость изображения.
4. Получить глобальный ReID-эмбеддинг и дополнительные интерпретируемые признаки.
5. Найти кандидатов в векторном индексе.
6. Переранжировать кандидатов по дополнительным признакам.
7. Вернуть Top-K, общий балл и объяснение результата.

Текущий MVP реализует пункты 3–7 на классическом визуальном дескрипторе. Это позволяет уже сейчас проверять API, хранилище, интерфейс и пользовательский сценарий.

## 3. Целевая архитектура

- модель: детектор автомобиля + vehicle ReID-энкодер;
- обработка: Python, Pillow/OpenCV, PyTorch;
- API: FastAPI после подключения внешних зависимостей;
- данные: PostgreSQL и pgvector; в MVP — SQLite;
- интерфейс: лёгкая web-панель оператора;
- поставка: Docker Compose, CPU-режим и опциональное GPU-ускорение.

## 4. Метрики

- Recall@1 и Recall@5 — находится ли правильный автомобиль среди первых результатов;
- mAP — качество ранжирования всех релевантных кадров;
- ROC-AUC и F1 — качество решения «тот же / другой автомобиль»;
- доля отказов при плохом качестве кадра;
- p50/p95 времени обработки одного изображения.

Разбиение данных выполняется по идентификатору автомобиля, а не случайно по изображениям. Иначе кадры одной машины попадут одновременно в обучение и тест, и метрики окажутся завышенными.

## 5. Сценарии обязательной проверки

- день/ночь, дождь, блики и низкое разрешение;
- передний, задний и боковой ракурсы;
- частичное перекрытие автомобиля;
- нечитаемый или отсутствующий номер;
- два автомобиля одной модели и цвета;
- изменение внешнего вида: грязь, сезонные колёса, небольшие повреждения;
- неизвестный автомобиль, которого нет в базе.

## 6. Главные риски

1. **Нет детектора в offline-MVP.** После получения данных подключить детекцию и оценить влияние ошибок обрезки.
2. **Порог совпадения пока эвристический.** Подобрать его на validation-наборе по целевой стоимости ложных совпадений.
3. **Смена ракурса.** Обучать ReID с hard-negative mining и ракурсными аугментациями.
4. **Похожие машины.** Добавить локальные признаки деталей и временно-пространственные ограничения камер, если они есть в данных.
5. **Утечка данных.** Разделять выборки по vehicle_id и камерам.

## 7. Критерии готовности конкурсной версии

- полный сценарий демонстрации выполняется без ручного вмешательства;
- метрики посчитаны воспроизводимым скриптом на зафиксированном split;
- порог решения выбран по данным, а не вручную;
- на неизвестном автомобиле сервис допускает ответ «совпадений нет»;
- есть инструкция запуска и резервная локальная сборка;
- минимум два участника независимо прошли демонстрационный сценарий.

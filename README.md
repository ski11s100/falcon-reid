# ФАЛЬКОН — цифровой признак транспортного средства

Сервис формирует устойчивое векторное представление автомобиля по его
визуальным характеристикам и находит тот же автомобиль на снимках с других
камер **без использования государственного регистрационного знака**.

Номер на всех кадрах размыт организатором, и ТЗ прямо запрещает опираться на
его остаточные признаки под угрозой дисквалификации. Решение работает с
формой кузова, цветом, геометрией, дисками, наклейками и повреждениями.

---

## 1. Архитектура решения

### Компонентная схема

```
                   ┌──────────────────────────┐
  кадр + BBox ───► │  service (FastAPI)       │
                   │  валидация, кроп,        │
                   │  инференс, OpenAPI       │
                   └────────┬─────────────────┘
                            │ вектор 2048
                   ┌────────▼─────────────────┐
                   │  PostgreSQL + pgvector   │
                   │  галерея, индекс HNSW    │
                   └────────┬─────────────────┘
                            │ Top-K + уверенность
                   ┌────────▼─────────────────┐
                   │  тонкий клиент, браузер  │
                   └──────────────────────────┘
```

Пакетный режим для проверки организаторами работает в обход сервиса:
`scripts/run_submission.py` читает CSV и каталог кадров и пишет три файла сдачи.

### Функциональные этапы

| Этап | Что происходит | Где реализовано |
|---|---|---|
| Получение | приём кадра и BBox, валидация, оценка качества | `service/app.py` |
| Обработка | кроп, препроцессинг, извлечение эмбеддинга | `falcon/extract.py` |
| Анализ | векторный поиск по галерее, косинусная близость | `service/repository.py` |
| Результат | Top-10, оценка уверенности либо обоснованный отказ | `falcon/submit.py` |

### Модель

`ResNet50-IBN-a` → `GeM pooling` → `BNNeck` → вектор 2048, 26.7 млн параметров,
**107 МБ** при лимите 2 ГБ.

Три решения, которые определяют качество:

**IBN (Instance-Batch Normalization).** Главная трудность задачи в том, что один
и тот же автомобиль на разных камерах выглядит по-разному: другое освещение,
баланс белого, время суток, погода. InstanceNorm нормирует статистики каждого
снимка по отдельности и вычищает «стиль» кадра, сохраняя содержание. IBN-a
ставит половину каналов под IN, половину под BN в первых трёх стадиях: низкие
слои избавляются от стиля, высокие сохраняют различающую информацию.

**BNNeck.** Triplet loss работает в евклидовом пространстве, а классификация
идентичностей — с косинусными углами. Считать обе по одному вектору значит
получить конфликтующие градиенты. BNNeck разводит их: triplet до BatchNorm,
классификация после, поиск — по вектору после BN.

**last_stride = 1.** Прореживание в последней стадии убрано, карта признаков
16×16 вместо 8×8. Признаки, которые задача просит различать — диски, наклейки,
повреждения — мелкие, терять по ним разрешение нельзя.

Вход 256×256. Пешеходный ReID использует вытянутые 128×256, но автомобиль в
кадре ближе к квадрату, и вытягивание искажает пропорции кузова — один из
основных различающих признаков.

## 2. Методы обработки данных и алгоритмы

### Обучение

Рецепт основан на «Bag of Tricks for Person Re-ID» (Luo et al., 2019):
ID-loss со сглаживанием меток 0.1 + batch-hard triplet + center loss с малым
весом, warmup 10 эпох, косинусное затухание скорости обучения, AMP fp16.

**PK-сэмплирование с кросс-камерным приоритетом.** Batch-hard triplet ищет
самый трудный позитив и негатив внутри батча, поэтому случайный батч бесполезен:
в нём нет пар одного ТС. Батч собирается как P идентичностей по K снимков, и
снимки одной машины берутся с *разных* камер. Это не косметика: в метрике
засчитываются только кросс-камерные совпадения, и учить модель надо ровно им.

**Аугментации** отвечают конкретным пунктам раздела 5 ТЗ про покрытие условий:
ColorJitter — время суток и погода; RandomErasing — частичное перекрытие;
Pad + RandomCrop — неточность рамки BBox; горизонтальное отражение — ракурсы.
Вертикальное отражение и сильный поворот не используются: камеры городской
инфраструктуры не переворачивают кадр.

### Поиск

Косинусная близость по L2-нормированным векторам. В сервисе — индекс HNSW
в pgvector; в пакетном режиме на конкурсной галерее из 750 объектов используется
точный перебор.

Это решение подкреплено измерением, а не предположением: на галерее 10 000
объектов приближённый поиск втрое **медленнее** точного и при этом теряет
соседей, точка перехода лежит около 100 000 объектов, а на 10⁶ HNSW даёт
ускорение ×7.5 при Recall@10 = 0.95. Полные замеры —
[docs/SCALABILITY.md](docs/SCALABILITY.md).

**k-reciprocal re-ranking** реализован в `falcon/rerank.py` в варианте,
совместимом с потоковым протоколом: используется только близость
«запрос → галерея» и «галерея → галерея». Классический алгоритм строит
совместную матрицу по объединению всех запросов и галереи и опирается в том
числе на связи «запрос — запрос», что ответ 38 организаторов прямо запрещает.
Независимость выдачи от состава остальных запросов закреплена тестом.

По умолчанию re-ranking **выключен**: на короткой галерее он ухудшал метрику,
и включать его следует только после A/B-проверки на локальном сплите.

### Оценка качества входа

Базовая валидация по разделу 4 ТЗ: размер кропа, резкость по дисперсии
градиента, яркость. Предупреждения показываются оператору, но не блокируют
обработку — решение о пригодности кадра остаётся за человеком.

## 3. Сборка и запуск

### Всё решение одной командой

```bash
docker compose up --build
```

Поднимаются PostgreSQL с pgvector и сервис инференса. Интерфейс оператора —
`http://localhost:8000`, спецификация OpenAPI — `http://localhost:8000/docs`.

Для GPU нужен установленный NVIDIA Container Toolkit. Сборка образа требует
интернета, запуск — нет: веса модели лежат внутри образа, во время инференса
ничего не скачивается.

### Генерация файлов сдачи

```bash
docker run --rm --gpus all -v /путь/к/данным:/data falcon-api \
    python scripts/run_submission.py /data --output /data/submission --threshold 0.42
```

Входной каталог должен содержать `test_query.csv`, `test_gallery.csv` и `images/`.
На выходе: `submission.csv`, `embeddings.npy`, `candidates.csv`, `manifest.json`.
Скрипт сам проверяет формат результата и завершается с ошибкой при расхождении.

### Локальная разработка без Docker

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install torch==2.14.0 torchvision==0.29.0 `
    --index-url https://download.pytorch.org/whl/cu126
$env:FALCON_CHECKPOINT = "models/best.pt"
.\.venv\Scripts\python.exe -m uvicorn service.app:app --port 8000
```

Без `FALCON_DATABASE_DSN` сервис использует локальный SQLite — удобно для
разработки, в docker-compose всегда подключён PostgreSQL.

### Полный цикл одной командой

От сырого датасета до готовых файлов сдачи:

```powershell
.\.venv\Scripts\python.exe scripts/run_pipeline.py D:/falcon-data --output runs/v1
```

Последовательно выполняются: аудит датасета, обучение с валидацией по
официальной метрике, калибровка порога отказа, A/B-проверка re-ranking,
проверка на остаточные признаки номера, генерация сдачи и замер
производительности. Каждый этап пишет свой отчёт в каталог результата.

Размер батча подбирается под доступную видеопамять автоматически. На Windows
это существенно: при нехватке видеопамяти драйвер не бросает ошибку, а начинает
вытеснять тензоры в системную память, и обучение молча замедляется в разы.

### Только обучение

```powershell
.\.venv\Scripts\python.exe falcon/train.py <каталог данных> --output runs/v1 --epochs 60
```

### Тесты

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

## 4. Формат сдачи

Формат подтверждён ответами организаторов на вопросы участников и закреплён
тестами в `tests/test_submission_format.py`.

| Файл | Правило |
|---|---|
| `embeddings.npy` | float32, `(len(query) + len(gallery), D)`. Сначала **все** query в порядке строк файла, затем **вся** gallery. Без дополнительной сортировки |
| `submission.csv` | `query_id` и ровно **10** `gallery_id`. Для каждого запроса без исключений, включая те, где мы уверены в отказе. Отказ в этом файле не выражается |
| `candidates.csv` | `query_id,gallery_id,confidence`. **Отказ = полное отсутствие строк** для этого `query_id`. Не пустая строка, не специальное значение |

`confidence` — оценка близости, не калиброванная вероятность. Диапазон
произвольный, требуется только монотонность по уверенности.

## 5. Протокол оценки и метрики

Официальный протокол реализован в `falcon/metrics.py` и покрыт 19 тестами.
Он отличается от «обычного» ReID-протокола, и это принципиально:

* **mAP@10** считается по `submission.csv`, не по полному ранжированию;
* **junk-фильтр** убирает из галереи объекты, у которых совпадают
  *одновременно* `vehicle_id` и `camera_id`. Объекты той же камеры с другим
  ТС остаются — это валидные и самые сложные негативы;
* фильтр применяется **до** усечения до десяти позиций;
* **AP нормируется на `min(n_pos, 10)`** — иначе ТС, снятое восемью камерами,
  не могло бы получить AP = 1 даже при идеальной выдаче;
* запросы без валидного позитива **исключаются** из mAP, а не получают AP = 0.

### Конкурсные данные

| Параметр | Значение |
|---|---|
| Кадров в `images/` | 11 416, полные кадры 1920×1080, JPEG |
| `train.csv` | 9 556 наблюдений, 1 541 автомобиль, 96 камер |
| `test_query.csv` / `test_gallery.csv` | 1 110 / 750 объектов |
| Снимков на автомобиль | от 4 до 8, в среднем 6.2 |
| Снято двумя и более камерами | 1 541 из 1 541, то есть 100% |
| Меньшая сторона кропа по BBox | минимум 173, медиана 376, максимум 511 пикс. |
| Доля площади кадра под рамкой | медиана 15.9% |

Съёмка дворовая и парковочная, ракурс преимущественно сверху. Номера и лица
размыты организатором. Проверка целостности — `scripts/check_data.py`.

Важное следствие для препроцессинга: кроп всегда вырезается из полного кадра
1920×1080, поэтому декодирование JPEG занимает заметную долю замеряемого цикла
и оптимизируется через `draft()` (см. `falcon/data.load_crop`).

### Локальный сплит

`falcon/data.py` строит из `train.csv` аналог закрытого теста: ID обучения и
валидации не пересекаются, у каждого закрытого запроса гарантирован
кросс-камерный позитив, и около **20% запросов не имеют пары в галерее** — та
же пропорция, что в закрытом тесте. Без такого сплита порог отказа калибровать
не на чем.

## 6. Обоснование порога отказа

Балл за режим кандидатов равен `10% × (0.7 × F1 + 0.3 × TNR)`. Оптимизировать
надо именно эту комбинацию: составляющие тянут в разные стороны. Низкий порог
отвечает на всё и обнуляет TNR, высокий отказывает на всём и обнуляет F1.

`falcon/calibrate.py` перебирает пороги по всему диапазону оценок и выбирает
максимум комбинации на локальном сплите с долей open-set запросов около 20%.
Метки закрытого теста не используются ни в каком виде.

Отчёт калибровки включает две базовые стратегии для сравнения — «всегда
отвечать» и «всегда отказывать» — чтобы на защите было видно, что именно даёт
выбранный порог.

> Итоговое значение порога и кривая заполняются после обучения на конкурсных
> данных. Переносить порог между моделями нельзя: положение максимума зависит
> от качества конкретной модели.

## 9. Ограничения и честные оговорки

* Модель на конкурсных данных ещё не обучена; в таблицах метрик стоят прочерки,
  а не заимствованные откуда-то числа.
* k-reciprocal re-ranking реализован, но выключен до проверки на реальной
  галерее.
* Отсутствие OCR в пайплайне не доказывает, что модель не опирается на
  остаточные признаки в зоне номера. Это нужно проверить экспериментом с
  дополнительным маскированием зоны — организаторы делают такую проверку для
  финалистов, и разумно провести её у себя заранее.
* Замеры масштабируемости сделаны на синтетических векторах с кластерной
  структурой, а не на эмбеддингах обученной модели — см. оговорки в
  [docs/SCALABILITY.md](docs/SCALABILITY.md).
* Проверка на остаточные признаки номера выполнена только на синтетике, где
  номеров нет вовсе. На конкурсных данных её нужно повторить: это защита от
  дисквалификации по разделу 9 ТЗ.
